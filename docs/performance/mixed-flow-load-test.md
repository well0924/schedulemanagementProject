## Mixed-flow 부하 테스트

> 분산 환경(App 2대 + Kafka 3-Broker) 운영 서버에서 측정했습니다. 상세 과정은 [블로그](https://codingweb.tistory.com/356)에 있습니다.

### 테스트 목적

이전 라운드는 think-time 없이 일정 생성만 반복한 스트레스 테스트였습니다.
이번에는 실제 사용에 가까운 조건(로그인 세션, 여러 API 혼합, 사용자 대기 시간)에서
서비스가 안정적으로 동작하는지, 그리고 비동기 파이프라인(Outbox → Kafka)이 따라오는지 확인합니다.

### 테스트 시나리오

| 항목 | 내용 |
|---|---|
| 흐름 | 로그인 1회 → 일정 생성 70% / 일정 수정 30% 반복 |
| think-time | 요청 사이 1~5초 무작위 (평균 3초) |
| 계정 | 테스트 계정 30개, 스레드 번호 기준으로 분배 |
| 일정 시간 | 스레드·반복마다 겹치지 않게 시작 시간을 배정 (충돌 409 방지) |
| 측정 | JMeter Aggregate Report(.jtl) + Grafana(HikariCP, JVM, Outbox, Kafka) |

### 목표 처리량 설정 — Little's Law

think-time이 있으면 처리량은 서버 성능이 아니라 요청 도착률이 결정합니다.

```
처리량 상한 ≈ VU ÷ (평균 응답 시간 + 평균 think-time)
  90VU  → 90 ÷ 3.04s ≈ 29.6 TPS
  490VU → 490 ÷ 3.07s ≈ 160 TPS
```

스트레스 테스트의 248.9 TPS를 같은 90VU에서 기대하면 안 되는 이유입니다.
목표는 처리량 숫자가 아니라 **상한에 도달하면서 에러 0%, 지연 안정, Outbox 백로그가 0으로 수렴하는 것**입니다.

### 결과

| 지표 | 90VU | 490VU |
|---|---|---|
| 요청 수 | 9,090 | 49,490 |
| 에러율 | **0.00%** | **0.00%** |
| 처리량 | 23.9 TPS (전체), 정상 구간 약 29 TPS | 109.6 TPS (전체), **정상 구간 157~161 TPS** |
| p50 / p95 / p99 | 36 / 75 / 150 ms | 46 / 142 / 469 ms |
| HikariCP 대기 | 0 | 0 (active 최대 약 8/40) |
| GC 정지 | 5ms 이하 | 7ms 이하 |
| Kafka 컨슈머 최대 지연 | 0.19s | 0.69s |
| Outbox 백로그 최대 | 약 33건 → 0 | **약 25,000건** (12:26~27 최고치, 테스트 종료 약 6분 뒤 0건) |

- 두 테스트 모두 Little's Law 상한에 도달했고, API 계층은 490VU에서도 안정적이었습니다.
- 490VU에서는 p99가 p50의 약 10배로 벌어졌습니다(90VU는 약 4배).

### 발견: Outbox 발행기 처리 한계

490VU에서 일정 생성은 초당 약 150건이었지만, 발행기는 초당 약 60~70건만 Kafka로 보냈습니다
(발행기 한 번 실행에 2~3초가 걸려 200건 ÷ 약 3~3.5초. 부하가 끝난 뒤 약 25,000건이 0이 되는 데 약 6분).

- **적체가 해소된 뒤 미발행 0건이었습니다.** `failed_message` 0건, 계정별 생성 건수 합계 34,300건이 JMeter 생성 요청 수와 일치.
- **원인:** 발행기가 이벤트마다 선점 UPDATE와 발행 완료 UPDATE를 따로 실행해, 한 주기(200건)에 DB 왕복이 약 400번이었습니다.
- **개선:** UPDATE 한 번으로 200건을 선점(`claim_id`)하고, 비동기로 발행한 뒤 성공 건을 일괄 완료 처리하도록 변경했습니다.

### 함께 발견한 문제

- **TIMESTAMP 2038 한계:** 첫 490VU 시도에서 2038-01-19 이후 시각의 일정 생성이 실패했습니다. `schedules.start_time`이 MySQL `TIMESTAMP`라 생기는 제품 버그로, `DATETIME` 전환이 필요합니다.
- **리마인더 미저장:** 테스트 데이터 점검 중, 커밋 이후 리스너에서 기본 전파(REQUIRED)로 저장해 리마인더가 저장되지 않던 버그를 발견했습니다. 위 결과는 리마인더 INSERT가 빠진 상태에서 측정한 값이며, 재측정에는 포함됩니다.
