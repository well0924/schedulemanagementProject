### 1단계: 50VU → 30VU → 50VU (안정 구간 확보)

최초 50VU에서 에러율 99.89%. 30VU로 낮춰 병목을 하나씩 제거한 뒤 50VU를 다시 달성했습니다.

| 차수 | VU | 에러율 | 원인 | 조치 |
|---|---|---|---|---|
| 1~2 | 50 | 99.89% | 서버당 풀 50개 × 2대 = 100개를 DB가 감당하지 못함 | 풀 20개로 하향, 빠른 회전 |
| 3 | 30 | 84.78% | JwtAuthenticationFilter가 요청마다 DB 조회로 커넥션 점유 | 회원 정보 Redis 캐싱 |
| 4 | 30 | 94.56% | nginx `worker_connections` 기본값 1024 초과 | 4096으로 상향, `multi_accept on`, epoll |
| 5 | 30 | 39.38% | 한 서버에 부하 집중 | round-robin → `least_conn` |
| 6 | 30 | 0.18% | — | 성공 |
| 7 | 50 | 81.4% | 풀 20개로는 50VU 동시 요청 처리 불가 | DB `max_connections` 200, 풀 60, minimum-idle 20 |
| 8 | 50 | **0.35%** | — | 30 TPS, 평균 1,613ms |

> 인증 필터 캐싱은 커넥션을 쓰는 요청 수를 줄였을 뿐, 트랜잭션이 길다는 근본 문제는 남아 있었습니다. 이 문제는 4~5단계에서 다시 다룹니다.

### 2단계: 60VU (에러율 16% → 0.05%)

| 차수 | 에러율 | 원인 | 조치 |
|---|---|---|---|
| 1 | 16% | 충돌 검사 쿼리의 `PESSIMISTIC_WRITE` → Gap Lock과 Insert Intention Lock 충돌(데드락) | 비관적 락 제거, COUNT 사전 검사, Lock Ordering, JDBC Batch |
| 2 | 약 50% | 알림 테이블 미생성 (`ddl-auto: none`) | DDL 실행 |
| 3 | 높음 | `@Transactional` 안에서 외부 API 응답을 기다리며 커넥션 점유 | `@Async`로 분리 |
| 4 | 높음 | 커넥션 고갈 후 nginx 타임아웃 초과(502) | nginx 타임아웃 10초, Redis Pre-check, 풀 확장 |
| 5 | 높음 | 모든 VU가 같은 userId로 요청 → 특정 행에 락 집중 | userId 1~1000 분산 |
| 6 | **0.05%** | — | 42.5 TPS |

### 3단계: 90VU 한계 규명 (84.3 TPS, 1분 37초 붕괴)

| 차수 | 샘플 | 에러율 | 평균 | 원인 |
|---|---|---|---|---|
| 1 | — | 3.24% | 5.7s | 409 Conflict 대량 발생, 같은 사용자 데이터 경합 |
| 3 | 7,019 | 41.40% | 856ms | Tomcat 스레드(90)와 Hikari 풀(60) 불균형으로 커넥션 고갈 |
| 4 | 5,934 | **8.04%** | 1,225ms | 1분 37초에 nginx 502/504 폭발, Tomcat 대기열(accept-count 200) 포화 |

- 조치: 고유 사용자 30,000명 CSV, minimum-idle = max, connection-timeout 3초 → 15초, 풀 40(서버당)
- 당시 진단: 폴링 스케줄러와 Kafka 콜백의 시점 불일치로 같은 행을 재처리하며 락 경합 → Kafka 콜백 기반 갱신을 **CAS 원자적 UPDATE**로 교체

> **이후 정정:** 4~5단계 재검증에서 slow query log에 폴러 UPDATE가 검출되지 않았고, 커넥션 대기가 Outbox 백로그보다 먼저 증가했습니다. 폴러는 붕괴의 원인이 아니라 결과였습니다.

### 4단계: CAS 도입 후 90VU 재검증

| 지표 | 1차 | 2차 | 3차 |
|---|---|---|---|
| 샘플 | 9,691 | 13,513 | 9,555 |
| 에러율 | 32.30% | 6.13% | **0.0%** |
| 평균 / 최대 | 1,027ms / 10,084ms | 1,322ms / 10,048ms | 1,564ms / 19,512ms |
| TPS | 76.7 | 56.3 | 52.4 |
| 붕괴 | 약 97초 | 약 120초 | 없음 |

- **원인:** CAS 경합이 아니라 `saveSchedule()` 트랜잭션 안에서 DB 왕복이 순차로 쌓인 구조. 알림 채널을 정하면서 `isEnabled(WEB)`, `isEnabled(PUSH)`를 따로 조회했습니다.
- **최대 응답이 10초에서 끊긴 이유:** nginx `proxy_read_timeout` 10초가 지나면 `proxy_next_upstream`이 요청을 다른 서버로 조용히 재전송했습니다.
- **조치:** 알림 `schedule_id` 인덱스, 카테고리 Redis 캐싱, 리마인더 생성을 AFTER_COMMIT으로 분리
- **새 병목:** 에러가 사라지자 Outbox 폴러의 처리 한계가 드러났습니다(1회 실행 최대 7.5초, 백로그 900건).

### 5단계: 쿼리 정리와 CAS 정합성 검증

| 지표 | 4차 | 5차 |
|---|---|---|
| 샘플 | 10,105 | 44,749 |
| 평균 / 최대 | 1,463ms / 5,153ms | **278ms** / 1,435ms |
| TPS | 55.8 | **249.2** |
| 에러율 | 0.00% | 0.00% |

- **리마인더 DELETE (2.6~3.2초):** 생성할 때도 기존 리마인더를 지우고 있었습니다 → 생성은 INSERT만, 수정만 DELETE + INSERT
- **충돌 검사 COUNT (1.7~2.6초):** 테스트 계정 하나에 10,272건이 쌓여 있었습니다 → 테스트 데이터 정리
- **기각한 가설:** CAS UPDATE가 커넥션 대기를 만든다 → slow query log에 해당 UPDATE 없음

**CAS 정합성 검증** (도입 이후 9월 데이터 전수 감사)

| 항목 | 결과 |
|---|---|
| 중복 이벤트 | 0건 (도입 전 4월 데이터에는 존재) |
| 멈춘 이벤트 (`sent=false`, `retry_count≥3`) | 0건 |
| 유실 이벤트 (일정은 있으나 Outbox 없음) | 0건 |

새로 드러난 문제: 생성 속도(249건/초)가 폴러 이론상 처리량(33.3건/초)의 7.5배

### 6단계: 폴러 튜닝과 최종 회귀 테스트

CAS 도입 전(3단계)과 같은 조건(풀 40, connection-timeout 15초, nginx read timeout 10초)에서 비교했습니다.

- **폴러 튜닝:** `fixedDelay` 3,000ms → 1,000ms, 배치 100 → 200건
- **ShedLock 설정 오류:** `lockAtLeastFor = "PT500MS"`는 ISO-8601에서 지원하지 않는 형식이라, 폴러가 매 실행마다 예외로 멈춰 있었습니다 → `"500"`으로 수정

| 지표 | 3단계 (CAS 도입 전) | 최종 |
|---|---|---|
| 처리량 | 84.3 TPS | **248.9 TPS** |
| 에러율 | 8.04% | **0.00%** |
| 평균 응답 | 1,225ms | **277ms** |
| 최대 응답 | 10,107ms | 1,572ms |
| 샘플 | 5,934 | 44,729 |
| 붕괴 | 1분 37초 | **재현되지 않음** |

튜닝 전에는 Outbox 백로그가 최대 11,000건까지 쌓였고, 튜닝 후 최종 테스트에서는 순간 2,000건까지 쌓였다가 0으로 수렴했습니다.
