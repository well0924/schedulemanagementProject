# 관측성과 테스트

## 관측성

부하 테스트의 병목은 모두 Prometheus와 Grafana 대시보드에서 찾았습니다. HikariCP 커넥션, JVM 힙과 GC, Outbox 백로그, Kafka 컨슈머 지연, 서킷브레이커 상태를 봅니다.

로그는 Loki로 모읍니다. MDC로 요청 ID와 이벤트 ID를 남겨 두어서, 한 이벤트의 컨슈머 처리, 재시도, DLQ, 재처리 로그를 이벤트 ID 하나로 묶어 볼 수 있습니다. 트레이스는 OpenTelemetry로 Tempo에 보내 요청 흐름(TraceID)별로 어느 구간에서 시간이 걸렸는지 확인합니다.

지표만으로 확정하기 어려운 DB 병목은 slow query log로 검증했습니다. 리마인더 DELETE와 충돌 검사 COUNT가 오래 걸린다는 것도 이 로그로 확인했습니다. 다만 기준 시간보다 짧은 쿼리가 여러 번 반복되는 비용은 이 로그에 남지 않아서, 커넥션 대기 지표와 함께 판단했습니다.

자세한 구성은 [모니터링](../monitoring/monitoring.md)과 [로깅](../monitoring/logging.md)에 있습니다.

## 테스트

| 종류 | 도구 | 확인하는 것 |
|---|---|---|
| 통합 테스트 | TestContainers | Kafka, Redis, MySQL을 컨테이너로 띄워 실제와 같은 조건에서 검증 |
| 외부 API 테스트 | WireMock | OpenAI 지연과 오류를 재현해 서킷브레이커와 타임아웃 동작 확인 |
| 동시성·정합성 테스트 | JUnit 5 | 배치 선점, 리마인더 선점, 컨슈머별 멱등성, WebSocket 구독 권한 등 운영 점검에서 고친 버그마다 재현 테스트 추가 |
| 부하 테스트 | JMeter | 스트레스 테스트(30~90VU), Mixed-flow 부하 테스트(90VU, 490VU) |

### 실패 경로 통합 테스트

실패했을 때의 동작은 단위 테스트로는 확인이 어려워서, 실제 컨슈머를 Kafka, MySQL, Redis 컨테이너 위에서 돌려 봤습니다.

컨슈머 실패 경로 테스트는 저장이 실패하면 3번 재시도한 뒤 DLQ로 가는지, 업무 데이터와 처리 기록이 함께 롤백되는지, 일시적인 장애가 지나간 뒤 정확히 1건만 처리되는지, 실시간 전달 시점에는 트랜잭션이 이미 끝나 있는지를 확인합니다. 수정 전 코드에서는 이 테스트가 실패합니다.

DLQ 재처리 테스트는 DLQ에 저장된 메시지를 스케줄러가 다시 발행하는지, 재발행한 메시지가 또 실패하면 같은 기록이 다시 열리고 횟수가 오르는지, 재발행 후 정상 처리되면 알림이 1건만 생기는지, 재시도를 다 쓰면 dead로 저장되는지를 확인합니다.

두 테스트 모두 CI 러너에서는 Kafka 컨테이너가 늦게 떠서 CI에서는 빼고, 로컬에서 `-Pit` 옵션으로 실행합니다.

### 부하 테스트 후 DB 대조

부하 테스트가 끝난 뒤에는 DB를 직접 조회해 결과를 맞춰 봤습니다. 490VU 기준으로 계정별 생성 건수 합계가 JMeter의 생성 요청 수(34,300건)와 일치했고, 미발행 Outbox와 재처리 대상(`failed_message`)은 0건이었습니다.
