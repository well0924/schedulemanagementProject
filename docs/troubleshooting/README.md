# 트러블슈팅

부하 테스트와 운영 점검에서 찾은 문제를 원인과 해결까지 정리했습니다. 성능 수치는 [성능 결과 요약](../performance/summary.md)에 있습니다.

## 성능 측정 중

### 1. Gap Lock 데드락 (60VU, 에러율 16%)

일정 충돌 검사 쿼리에 `PESSIMISTIC_WRITE`를 걸어 두었는데, 시간 범위가 겹치는 트랜잭션끼리 Gap Lock을 잡으려다 서로 막히면서 데드락이 났습니다.

비관적 락을 빼고 COUNT로 먼저 겹치는 일정이 있는지 확인하도록 바꿨습니다. 확인과 저장 사이에 다른 요청이 끼어드는 경우는 `(member_id, start_time)` UNIQUE 제약이 막습니다. Redis 분산락도 검토했지만, DB에서 생긴 문제를 애플리케이션 계층에서 돌아가는 방식이라 택하지 않았습니다.

### 2. 커넥션 풀 고갈: 반쪽짜리 정답에서 근본 원인까지

30VU에서 트랜잭션이 길어 커넥션을 오래 잡고 있었고, 결국 풀이 바닥났습니다.

처음에는 JwtFilter가 요청마다 하던 회원 조회를 Redis 캐싱으로 바꿔 50VU까지 버티게 했습니다. 하지만 이건 커넥션을 쓰는 요청 수만 줄였을 뿐, 트랜잭션이 길다는 문제는 그대로였습니다.

90VU 재검증 때 트랜잭션 안의 중복 조회를 없애고, 리마인더 저장을 커밋 이후로 옮기고(나중에 다시 같은 트랜잭션으로 되돌렸습니다. 5번 참고), 불필요한 DELETE와 쌓여 있던 테스트 데이터를 정리했습니다. 평균 응답이 1,463ms에서 278ms로 줄었습니다.

### 3. 응답이 매번 정확히 10초에서 끊기는 현상

최대 응답 시간이 매번 10초 근처에서 잘리고, 에러는 일부만 기록됐습니다.

실제로 10초 걸린 게 아니라 nginx `proxy_read_timeout`(10초)에 걸려 504로 끊긴 것이었습니다. 처음에는 `proxy_next_upstream`이 다른 서버로 다시 보낸 것으로 해석했는데, 그랬다면 두 번째 서버까지 기다려 약 20초에서 끊겼어야 합니다. nginx는 `non_idempotent` 설정 없이는 이미 보낸 POST를 다른 서버로 다시 보내지 않습니다. 타임아웃을 늘려 보니 실제 최악 응답은 19.5초였습니다.

이 현상으로, 3단계에서 "99% 응답 10초는 커넥션을 오래 잡고 있어서"라고 했던 진단이 틀렸다는 걸 확인했습니다.

### 4. 90VU 붕괴에서 배치 선점까지

3단계에서는 Outbox 폴링의 락 경합이 붕괴 원인이라고 봤습니다.

다시 확인해 보니 HikariCP 대기 스레드가 Outbox 백로그보다 약 90초 먼저 늘어났습니다. 같은 구간의 slow query log(`long_query_time=0.05`)에서는 폴러 UPDATE가 보이지 않았고, 대신 일정 생성 중 리마인더 DELETE와 충돌 검사 COUNT가 오래 걸렸습니다. 그래서 이 쿼리와 트랜잭션 구조부터 고쳤습니다.

이때 정정한 것도 있습니다. 당시 "CAS"라고 불렀던 `UPDATE … SET retry_count = retry_count + 1 WHERE id = ? AND sent = false`는 재시도 횟수만 바꾸고 바로 커밋돼서, 다른 실행도 같은 조건을 통과할 수 있었습니다. 실제로 한 번만 처리되게 한 건 이 쿼리가 아니라 ShedLock(발행기를 한 대에서만 실행)과 컨슈머 멱등 처리였습니다.

490VU에서는 발행기 자체가 한계였습니다. 건마다 조건부 UPDATE와 완료 UPDATE를 따로 실행해 한 주기에 DB 왕복이 약 400번 있었고, 한 번 도는 데 2~3초가 걸려 초당 60~70건이 최대였습니다. 그래서 UPDATE 한 번으로 200건에 `claim_id`와 선점 시각을 기록하고, 선점되지 않았거나 30초가 지난 행만 가져오도록 바꿨습니다. 이제 선점 자체가 다른 실행을 막고, 비동기로 발행한 뒤 한꺼번에 완료 처리합니다.

### 5. 배치 선점 후 재측정에서 드러난 커넥션 고갈 두 건

첫 번째는 시작 1~2분에 나타났습니다. 리마인더 리스너가 `AFTER_COMMIT` + `REQUIRES_NEW`였는데, Spring은 AFTER_COMMIT 리스너가 끝날 때까지 원래 커넥션을 반납하지 않아서 새 트랜잭션이 커넥션을 하나 더 요청했습니다. 490VU에서 서버당 40개인 풀이 바닥나 15초 타임아웃과 502가 났습니다. 리마인더를 같은 트랜잭션(`BEFORE_COMMIT`)에서 저장하도록 바꿨습니다.

두 번째는 시작 약 4분에 나타났습니다. 두 서버의 풀이 동시에 고갈됐는데 RDS의 CPU와 디스크 크레딧은 여유가 있었습니다. `UPDATE … ORDER BY created_at LIMIT 200`이 REPEATABLE READ에서 미발행 구간 끝의 간격까지 잠가 새 Outbox INSERT를 막은 것으로 보고, 선점 트랜잭션만 `READ_COMMITTED`로 바꿨더니 고갈이 사라졌습니다.

이 두 건을 겪고 나서, 부수 작업은 같은 트랜잭션에서 하거나 Outbox로 비동기 처리하는 것 둘 중 하나로만 하기로 정했습니다. 커밋 이후 리스너에서는 DB에 쓰지 않습니다.

### 6. JVM Full GC 반복
G1GC를 튜닝하고 모니터링 서버를 분리해서, 서비스 서버와 자원을 나눠 쓰지 않게 했습니다.

## 운영 점검 중 찾은 버그

부하 테스트와 기능 점검을 운영 환경에서 직접 돌리면서, 로컬에서는 보이지 않던 버그를 찾아 고쳤습니다.

| 버그 | 원인 | 해결 |
|---|---|---|
| 리마인더 알림이 저장되지 않음 | 커밋 이후 리스너에서 기본 전파(REQUIRED)로 저장 → 이미 끝난 트랜잭션에 참여해 예외 없이 버려짐. 9월 11일 이후 부하 테스트에도 리마인더 INSERT가 빠져 있었음 | 같은 트랜잭션(`BEFORE_COMMIT`)에서 저장 (`REQUIRES_NEW`로 먼저 고쳤다가 고부하에서 커넥션 2개 문제가 생겨 다시 변경) |
| 챗봇 이력이 한쪽 컨슈머에만 반영 | 두 컨슈머 그룹이 `event_id`만으로 중복을 막아, 먼저 처리한 그룹이 다른 그룹을 막음 | 멱등성 키를 `(consumer, event_id)`로 변경 |
| 운영에서 테이블 3개 누락 | 엔티티만 있고 마이그레이션이 없었음. 로컬은 `ddl-auto: update`가 대신 만들어 줘서 드러나지 않음 | Flyway 마이그레이션 추가 |
| 알림 DLQ 스케줄러가 회원가입 메시지까지 재처리 | 메시지 타입 필터 없음 | 타입 필터 추가 (아래 매퍼 누락 때문에 실제로는 이 필터도 동작하지 않았음) |
| 챗봇 서킷브레이커 설정이 적용되지 않음 | 코드의 인스턴스 이름과 설정 파일 이름 불일치, 타임아웃 단위 오류 | 이름 통일, 단위 수정, 대체 응답은 이력에서 제외 |
| WebSocket 구독에 인증이 없음 | 다른 회원의 알림 채널도 구독 가능 | 연결할 때 토큰 검증, 본인 채널만 구독 허용 |
| 리마인더 중복 발송 | 서버 2대가 같은 리마인더를 동시에 발송 | ShedLock + 행 단위 선점 UPDATE |
| 같은 아이디로 회원이 2명 생성 | `member.user_id`에 UNIQUE 없음 → 로그인 실패 | UNIQUE 제약 추가 |
| 컨슈머 실패 메시지가 재시도·DLQ 없이 사라짐 | 알림·회원가입 컨슈머가 일반 예외를 삼켰고, 알림 컨슈머는 처리 시작 시점에 Redis "processing" 키를 잡아 재시도를 버렸음. 처리 기록이 `REQUIRES_NEW`로 따로 커밋돼 챗봇 컨슈머는 실패해도 "처리됨"이 먼저 남음 | 업무 저장과 처리 기록을 한 트랜잭션으로, 실패는 예외로 전파, 완료 후에만 Redis 표시. 실제 Kafka 통합 테스트로 수정 전 코드는 DLQ에 도달하지 않고 수정 후엔 재시도 3회 → DLQ, 롤백되는 것을 확인 |
| 재처리 메시지가 원래와 다른 파티션으로 감 | 재처리 재발행을 키 없이 보냈고, 리마인더는 일정 ID가 아니라 알림 행 ID를 키로 씀 | 재발행에 대상 ID 키 추가, 리마인더 키를 일정 ID로 통일 |
| DLQ 재처리가 한 번도 동작하지 않음 | 매퍼가 실패 기록의 `messageType`·`dead`를 빠뜨려 알림 스케줄러는 `Set.contains(null)`로 NPE, 회원가입 스케줄러는 대상 0건. 알림 DLQ 기록에 다음 재시도 시각이 비어 조회되지 않음. 재발행 직후 해결로 표시해 다시 실패하면 "이미 기록됨"으로 버림. 전송 결과를 기다리지 않아 실패도 성공으로 기록. Flyway에 `event_id`, `next_retry_time` 컬럼 없음 | 매퍼 필드 추가, 재시도 시각 설정, 재실패 시 같은 기록을 다시 열어 횟수 증가, 전송 응답 대기, 컬럼 추가 마이그레이션. 단위 테스트는 목 모델이라 매퍼 누락을 놓쳐, 실제 Kafka·MySQL 통합 테스트로 확인 (매퍼 수정을 되돌리면 같은 NPE로 실패) |
| CI가 배포 이미지를 만들지 않음 | `jibDockerBuild`라 이미지가 러너 안에서만 만들어지고 사라져, 배포가 Docker Hub의 옛 이미지를 받음. 이미지에 비밀값도 들어 있었음 | main push 때 `jib`으로 push, 비밀값은 서버 `.env`로만 주입, 서버 2대 순차 배포 |

## 남은 한계

| 한계 | 영향 | 다음 단계 |
|---|---|---|
| 소셜 로그인이 nginx `ip_hash`에 의존 | OAuth2 인증 요청을 서버 세션에 저장해, 같은 서버로 돌아와야만 로그인이 완료됨 | 서명된 쿠키 기반 저장소로 바꿔 서버 간 상태 공유 제거 |
| 실시간 알림이 서버별로 분리 | WebSocket 브로커가 서버마다 따로 있어, 다른 서버에 연결된 사용자에게는 실시간 알림이 가지 않음(알림 내역은 저장됨) | Redis Pub/Sub 또는 Kafka 브로드캐스트로 서버 간 전달 |
| 인프라 서버 단일 호스트 | Kafka 브로커 3개, Redis, Nginx가 EC2 한 대에 있음. 브로커 프로세스 장애에는 복제로 대응하지만, 호스트 장애 시에는 이벤트 발행·캐시·라우팅이 함께 멈춤 (앱 서버 2대 이중화는 애플리케이션 계층에만 해당) | 브로커를 서로 다른 호스트·가용 영역으로 분산 |
| Redis 단일 장애점 | 캐시, ShedLock, 중복 사전 검사가 모두 Redis에 의존 | Redis Sentinel 또는 장애 시 동작 정의 |
| `TIMESTAMP` 2038년 한계 | 2038-01-19 이후 시각의 일정을 저장할 수 없음 (490VU 테스트 중 발견) | `DATETIME`으로 전환하는 마이그레이션 |
| 챗봇 이벤트 DLQ 미처리 | 챗봇 컨슈머 실패는 `chat-history.DLQ`, 발행 실패는 `chat-events.DLQ`로 가지만 둘 다 받는 컨슈머가 없어 재처리되지 않음 | DLQ 토픽 이름을 통일하고 알림처럼 `failed_message` → 재처리 연결 |
| DLQ 경로의 남은 유실 지점 | DLQ 컨슈머는 기록 저장에 실패하면 예외를 삼켜, DB 장애 중 들어온 DLQ 메시지가 사라질 수 있음. 웹 푸시 재처리가 다시 실패하면 새 기록을 만드는데 payload 유니크 제약에 걸려 남지 않을 수 있음 | DLQ 컨슈머 실패를 에러 핸들러로 전파(간격 있는 재시도), 웹 푸시 재처리 실패를 스케줄러가 받아 같은 기록의 횟수 증가 |
| retry 토픽 이름과 실제 지연 불일치 | `retry.5s`~`retry.60s` 토픽은 받자마자 원래 토픽으로 넘겨 실제로 기다리지 않음. 지연은 기록의 다음 재시도 시각과 30초 주기 스케줄러가 만듦 | 토픽을 하나로 줄이거나, 실제 지연이 필요하면 지연 재시도 토픽(`@RetryableTopic`) 도입 |
| DB 쓰기 증가로 API 응답 시간 증가 | 배치 선점 후 490VU에서 평균 응답 65ms → 804ms (리마인더 INSERT 추가, 컨슈머 처리량 약 2배) | 원인 분리 측정, 리마인더 생성을 Outbox로 이동, 컨슈머 동시성 조정 |
