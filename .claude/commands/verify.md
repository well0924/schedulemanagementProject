## 언제 쓰는가

부하테스트 재검증, 기능 e2e 검증처럼 "이렇게 될 것이다"는 가설을 실제로 확인해야 할 때. 결과를 그냥 받아 적지 않고, 반드시 소스 코드까지 대조해서 검증한다.

## 절차

1. **가설**: 무엇을 기대하는지, 왜 그렇게 기대하는지를 이전 데이터·코드 근거와 함께 먼저 정리한다.
2. **실측**: 실제 테스트/실행 결과를 받는다 (사용자가 직접 실행하고 결과를 공유).
3. **코드대조**: 결과가 가설과 다르든 같든, 관련 소스 코드를 직접 열어 실제 동작과 대조한다. 블로그 요약·이전 대화 요약·자동 요약 도구의 결과를 그대로 믿지 않고 항상 소스로 재확인한다.
4. **기록**: 원인-해결-성과 형식으로 정리한다. 필요하면 메모리·블로그·이력서 반영 여부를 확인한다.

## 규칙

- 3번(코드대조)은 생략하지 않는다 — 결과가 가설과 맞아떨어져도 최소 한 곳은 소스로 확인한다.
- 가설이 틀렸을 때는 "누구의 가설이 틀렸는지"(사용자 vs Claude)를 구분해서 기록한다. Claude가 근거 없이 만든 추정과 사용자가 원래 세운 가설을 섞지 않는다.
- 가설이 맞았을 때도 마찬가지로 "누구의 가설이었는지"를 기록한다. 결과가 맞고 틀리고와 무관하게 출처는 항상 남긴다 — 맞은 것만 조용히 넘어가지 않는다.
- 기록 단계에서 과장하지 않는다. 아직 검증되지 않은 것은 "검증 예정"으로, 검증이 끝난 것만 "확인됨"으로 표기한다.

## 입력

$ARGUMENTS 로 이번에 검증할 가설이나 대상을 전달한다. 비어 있으면 직전 대화에서 나온 가설을 확인하고 이어서 진행한다.
